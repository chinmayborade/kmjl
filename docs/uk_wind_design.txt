1. Purpose
This document turns the product manager's brief into a buildable plan. It covers the
problem as we understand it, the assumptions we are making, the data logic, the
architecture, the API, the UI, testing, deployment, the 16-hour plan, and the outline for
both parts of the video. It is meant to be the single reference while building, and the base
for the README and the tech-lead walkthrough.
2. Problem Understanding
The client is a UK energy utility. Their day-ahead buying team must decide, on day D-1, how
much power to buy for delivery day D. Wind is weather-dependent, so the amount to
procure from other sources (for example thermal plants) is demand minus expected wind.
They have only wind forecasts to rely on, and those forecasts have errors.
The portal must let them:
1. See the latest wind generation forecast that was actually available when they had to
make the decision.
2. Measure forecast accuracy quantitatively so they can plan around the expected error.
Scope is limited to national-level wind data from Elexon only, for purchase decisions made
in January 2026.
What a good answer looks like
The forecast shown for a delivery day is the latest one published before the decision
cutoff, never a later one (no hindsight).
Accuracy is reported in a way a trader can act on: in megawatts, by forecast horizon,
with error ranges rather than a single number.
The tool states its assumptions openly (cutoff time, time zone, metric definitions).

4.2 Forecasts (WINDFOR)
Endpoint: Elexon BMRS datasets WINDFOR stream.
Key fields: startTime (target time), publishTime (when the forecast was made),
generation (forecast MW).
4.3 Data quirks to check during exploration
Whether WINDFOR is hourly or half-hourly, and how far ahead it goes. If hourly, decide
how to align with 30-minute actuals (either compare on the hour only, or forward-fill
within the hour, documented explicitly).
Duplicate or overlapping publishes for the same target.
Gaps, zero values, and negative or null values.
API pagination and date-range limits on the stream endpoints.
5. Core Logic
5.1 Decision forecast (the most important rule)
For a delivery day D and cutoff time C on day D-1:
1. Take all forecast rows whose startTime falls on day D.
2. Keep only rows with publishTime <= C.
3. For each startTime, keep the row with the latest publishTime.
4. Result: the set of target periods for day D as the trader would have seen them.
Implementation note: in pandas, sort by publishTime, filter, then drop_duplicates on
startTime keeping the last. This is simple and easy to unit test. Avoid clever joins where a
plain filter is clearer.
5.2 Forecast horizon
Horizon = startTime minus publishTime, in hours. Every metric can be sliced by horizon
bucket (for example 0 to 6h, 6 to 12h, 12 to 24h, 24 to 48h, 48h+). For the decision view, the
relevant horizon is whatever the cutoff implies for each period (roughly 14 to 38 hours for
a 10:00 cutoff on D-1).
5.3 Joining with actuals
Inner join the decision forecast to actuals on startTime. Keep an outer join internally to
count missing data, and expose coverage numbers (periods with forecast, with actual,
with both).

6. Accuracy Metrics
Define error = forecast minus actual (positive means over-forecast, which risks under-
buying other power).
Note on MAPE: avoid it as a headline metric. Wind output can approach zero, which makes
percentage error unstable. If shown at all, explain the caveat.
Error-aware view
Using historical signed-error quantiles (by horizon bucket), draw a band around the
forecast, for example forecast minus P90 error up to forecast minus P10 error. This
answers the client's second need: decisions that consider the quantified error. Caveat for
the video: in-sample quantiles over one month are descriptive, not a guarantee. Say so
plainly.

Design principles
One deployable container: FastAPI serves the API and the built React static files. One
URL, no CORS issues, simple deployment.
Data is ingested ahead of time and read from local storage. The app does not depend
on Elexon being up during the demo.
Pure functions for the logic (decision selection, metrics) separate from I/O, so they are
easy to test.
Configuration through environment variables (cutoff time, data path, default dates).

9. Frontend Design
Three views in one single-page app, with a shared date picker and a visible assumptions
panel.
1. Decision view: choose a delivery date. Show the 48 half-hourly forecast values
available at the cutoff, with publishTime shown, and the actual overlaid once the day
has passed. Headline cards: total forecast energy, peak, and minimum.
2. Accuracy view: metric cards (MAE, RMSE, bias, P90 error), error histogram, and error
versus horizon chart. Include a clear plain-language explanation of each metric.
3. Risk view: forecast with the uncertainty band, and a simple readout such as "in 90
percent of past cases the wind outturn was within X MW of the forecast at this
horizon".
UX rules: loading and empty states, explicit units (MW), consistent time zone, and no
chart that cannot be explained in one sentence.

11. Testing Strategy
Prioritise by risk, not by coverage numbers.
Decision selection: synthetic data proving that forecasts published after the cutoff are
excluded, that the latest earlier publish wins, and that boundary equality (publishTime
equal to cutoff) behaves as documented.
Metrics: hand-computed small examples for bias, MAE, RMSE and percentiles.
Alignment: hourly versus half-hourly handling.
API: a few contract tests with FastAPI TestClient against a tiny fixture dataset.
Smoke test in CI: build the Docker image and hit /api/health.
12. Deployment
Multi-stage Dockerfile: Node stage builds the React app, Python stage installs
dependencies, copies the build output and cached data, and runs uvicorn on the port
provided by the platform.

15. Video Outline (10 minutes maximum)
Part 1: Client pitch (about 4.5 minutes)
1. The problem in the client's words: buying the gap between demand and wind, a day
ahead, under uncertainty (45 seconds).
2. Live demo, decision view: pick a January date and show exactly what they would have
seen at the cutoff (90 seconds).
3. Accuracy view: how good the forecasts were, in MW, by horizon (75 seconds).
4. Risk view: how to use the error band when deciding how much to hedge (60 seconds).
5. Close: what the pilot proves and the next steps, such as adding demand and other data
(30 seconds).
Part 2: Tech lead review (about 5 minutes)
1. Architecture diagram and why one container (60 seconds).
2. The decision-forecast rule and its tests, shown in code (90 seconds).
3. Metrics definitions and the horizon slicing (60 seconds).
4. Repo tour, config, and how to run (60 seconds).
5. Practices: tests, Docker, assumptions list, AI tool disclosure, known limitations and
what you would do next (30 seconds).
Tip: script it, rehearse once, and record in one or two takes. The video is evaluated first, so
a clear and confident walkthrough matters more than extra features.
